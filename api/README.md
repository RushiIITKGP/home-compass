# api

FastAPI + LangGraph agent — the orchestration layer from architecture
sheet A-01, with the confidence-gated conversation flow from A-02.

## Files

- **`agent.py`** — the StateGraph: intake → confidence → gate →
  clarify **or** retrieve → tools → (synthesis **or** present,
  depending on which tool was actually called — see below)
- **`setup.py`** — the one place Gemini + the three MCP servers this
  graph actually uses (mcp-property, mcp-enrich, mcp-market) + the
  Postgres checkpointer get wired together, shared by `cli.py` and `main.py`
- **`cli.py`** — terminal harness (Phase 3)
- **`main.py`** — FastAPI gateway with SSE streaming (Phase 4)

## Phase 5 — enrichment tools (mcp-enrich, mcp-market)

Built in Phase 5: `get_neighborhood_demographics`, `get_safety_stats`,
`get_market_trends`, plus amenities via the pre-built OSM server. How
and when these actually get called changed after Phase 5 shipped — see
"Search returns exactly what was asked for" below for the current
design and the full reasoning.

## Live status updates while the agent works

Each node writes a short, human-readable status line via `_status()` in
`agent.py` — "Reading your message...", "Searching listings...",
"Gathering neighborhood data...", etc. — using LangGraph's
`get_stream_writer()`. `main.py` streams these to the client as
`{"status": "..."}` SSE events, interleaved with the actual response
tokens, so the frontend can show a live "what's happening right now"
log instead of a silent pause between sending a message and seeing a
reply (see `web/components/StatusLog.tsx`).

This runs through the same unified stream as token output —
`graph.astream(..., stream_mode=["custom", "messages"])` — rather than
two separate mechanisms; `astream_events` (used through Phase 6) never
surfaced custom writer output at all, confirmed by testing both APIs
directly before switching. `get_stream_writer()` is safe to call even
outside a streaming context (verified directly), so this required no
changes anywhere that calls the graph via plain `.invoke()`/`.ainvoke()`
— every existing test in this project still passes unmodified.

**These status lines are 100% hardcoded** — `TOOL_STATUS_MESSAGES` is a
plain dict, no LLM call involved. Worth knowing this is one of two
genuinely different patterns products like Claude Code use for similar
live-status displays: per Anthropic's docs, a `tool_use` block already
carries the tool's `name` and `input` fully structured, so a label like
"Ran a command" can be derived directly from that with zero extra
inference — same mechanism as our dict lookup. *Extended thinking*
content, by contrast, is genuinely LLM-generated (streamed via
`thinking_delta` events as the model actually produces it, and even
its summarized form is generated by a separate summarizer model, not a
template) — a fundamentally different, more expensive mechanism this
project doesn't use. If Home Compass ever wanted a narrated "here's
what I'm reasoning through" line rather than "here's which tool I
called," that would need an actual model call per status update, not
an extension of `TOOL_STATUS_MESSAGES`.

## No more manual `export` — `.env` loads automatically everywhere

Every entry point in this project — `cli.py`, `main.py`, and all three
`server.py` files, `backfill_embeddings.py`, `ingest_market_data.py`,
`seed_kaggle.py` — now calls `load_dotenv()` before importing anything
that reads environment variables. That ordering matters: `setup.py`,
`db/session.py`, and `embeddings.py` all read values like
`DATABASE_URL` at **module-import time**, not lazily — importing them
before `.env` was loaded meant those reads silently fell back to
hardcoded defaults instead of picking up `.env`, confirmed with a
minimal reproduction before fixing it. `export`ing a value still works
as a one-off override and takes priority, but was never actually
required once `.env` has real values in it.

## Search returns exactly what was asked for — enrichment is on demand

A search only ever calls `search_listings` and presents the raw
results — no automatic demographics, crime, or market lookups. Every
result gets a flat 0.4 `recommendation_confidence` (the honest
baseline: nothing beyond the listing itself has been verified) and an
empty `enrichment` object. This used to be different — a fresh search
automatically ran a full `enrichment_node` pass (demographics, crime,
market, amenities) for every result whether or not anyone asked.
Removed on request: enrichment should only cost a network/API call
when the user actually wants that information.

**How a later question gets answered.** `retrieve_node`'s LLM is bound
to `search_listings` **and** the three enrichment tools
(`get_neighborhood_demographics`, `get_safety_stats`,
`get_market_trends`). If you ask "what's the crime rate near that
listing?" after a search already ran, the agent calls
`get_safety_stats` directly — not a new search, not silence. Amenities
stays unreachable from this path: its real schema needs a two-step
geocode-then-query-nearby flow (A-08) judged too fragile for the LLM
to invoke ad hoc, and its only caller (`enrichment_node`) is no longer
wired into the graph — a real, known gap, not an oversight (see
`make_enrichment_node()`'s docstring for the tradeoff and how to
re-enable it).

**`route_after_tools()` is what makes this work.** It checks which
tool actually got called this turn: `search_listings` present → route
to `synthesis` (format results for display, no enrichment fetched).
Only an enrichment tool called directly → route straight to `present`,
skipping `synthesis` too, since there's nothing new to rank — the
fresh result is already visible to `present_node` as a `ToolMessage`
in conversation history. Verified with a call-counter test: after a
fresh search, demographics/safety/market are called **zero** times;
after a follow-up asking specifically about crime, only
`get_safety_stats` gets called, once.

**Known tradeoff, stated plainly:** `state["recommendations"]` only
gets (re)computed when a search actually runs, so if you ask a
follow-up and then look at a `ListingCard` from that same turn, it'll
still show the 0.4 baseline / empty enrichment, not the fresh data —
even though the chat reply itself correctly uses it.
`present_node`'s prompt reads recent conversation history, not just
`state["recommendations"]`, so the reply is accurate; the card display
just doesn't retroactively update from a follow-up. Re-running a
search re-syncs both — and if a follow-up happened to ask about a ZIP
that gets searched again later, `synthesis_node` picks up whatever's
already cached in `state["enrichment"]` from that follow-up rather
than treating it as unverified.

## Context window management (A-04)

Every LLM call (`intake`, `clarify`, `retrieve`, `present`) uses
`_recent_messages()` instead of the full checkpointer history — trimmed
to the last `CONTEXT_WINDOW_TURNS` (default 8) user turns, at whole-turn
boundaries so a tool-call/tool-response pair from an older turn never
gets split in half.

This doesn't lose anything that matters: whatever the user stated in a
now-trimmed turn was already extracted into `state["slots"]` by
`intake_node` at the time, and slots persist via the checkpointer
regardless of how much raw message history gets dropped. A 10-turn
conversation test confirms this — the agent still correctly remembers
turn 1's stated location at turn 10, even though the actual prompt sent
to the LLM on turn 10 no longer contains turn 1's raw text at all. See
`_recent_messages()`'s docstring for why this makes a separate
summarization step unnecessary here, unlike a general-purpose chatbot
that has no structured memory to fall back on.

## Known-fixed bug: streamed tokens showing up as "[object Object]"

`AIMessageChunk.content` is usually a plain string, but some Gemini
responses return a **list of content blocks** instead —
`[{"type": "text", "text": "..."}]` — sometimes mixed with non-text
blocks (reasoning/thinking traces) that shouldn't reach the user at
all. Sending that list straight into an SSE `token` field broke the
frontend's contract (`token` is typed as `string`): concatenating a
list of objects onto a JS string coerces each object to the literal
text `"[object Object]"`. Fixed with `_extract_text()` in `main.py`,
which normalizes both shapes into a real string and filters out
anything that isn't a `type: "text"` block before it's ever streamed.

## Known-fixed bug: empty response bubble (no visible text at all)

Different failure mode from the `[object Object]` bug above, but the
same underlying weakness: `present_node`/`clarify_node` never checked
whether the LLM's response actually contained usable text before
passing it along. If a response came back empty — content-blocks with
no `text`-type block in them, or otherwise blocked/filtered — the user
saw a completely empty bubble, silently.

Two-part fix:
1. **`agent.py`** — `present_node` and `clarify_node` now check
   `extract_text_content(response.content)`; if it's empty, they build
   a deterministic fallback (`_fallback_summary()` for present, a
   templated question for clarify) from data already in state, rather
   than shipping silence. `cli.py` and `main.py` both use the same
   shared `extract_text_content()` now instead of each guessing at the
   content shape separately.
2. **`main.py`** — even with that fallback in place, a message built
   directly in Python (not streamed from an LLM call) would never
   generate an `on_chat_model_stream` event, and the frontend only ever
   populates a message's text from token events, never from `done`. So
   `stream_chat` now tracks whether *any* text actually streamed during
   a turn, and if not, sends the real final message as one last token
   before `done` — closing the gap between "the backend has the right
   text" and "the frontend actually shows it."

**Honest limit:** this hardens the system against several plausible
causes (content-blocks-only responses, safety-filtered completions) and
is verified end-to-end for those. It isn't a substitute for seeing what
actually happened in a specific failing call. If this recurs, the
fastest path to a definitive answer is enabling LangSmith tracing —
`LANGCHAIN_TRACING_V2=true` and `LANGCHAIN_API_KEY` are already in
`.env.example` from Phase 0 and take effect automatically once set, no
code changes needed. That gets you the actual raw response for the
specific turn instead of a screenshot-based guess.

## One LLM provider, one key

The chat model and the embedding model (used by `mcp-property`) both
read the same `GEMINI_API_KEY` — no second provider or key anywhere in
this project.

## Try the CLI or HTTP API

Fill in `.env` at the repo root (`GEMINI_API_KEY` etc. — see
`.env.example`), then:

```
pip install -r requirements.txt -r ../requirements.txt \
  -r ../mcp-property/requirements.txt -r ../mcp-enrich/requirements.txt -r ../mcp-market/requirements.txt

python cli.py
# or
uvicorn main:app --reload --port 8080
```

No `export` needed — both entry points call `load_dotenv()` before
importing `setup`/`agent`, so `.env` loads automatically regardless of
which directory you run the command from. `export`ing a value still
works if you want to override something for one run without editing
`.env`.

mcp-amenities (the pre-built OSM server) isn't spawned by
`api/setup.py` — it's not currently called by the agent at all (see
`mcp-amenities/README.md`). Node.js isn't required to run the backend
as it stands today; it's only needed for the frontend.

## Testing without live API keys

Every piece of Phase 5's enrichment logic was validated for real: the
Census and FBI response-parsing functions against realistic mocked
HTTP responses (including the `-666666666` Census "no data" sentinel
and network failures), and the full retrieval → enrichment → format →
present flow end-to-end against a **real local Postgres** with the
**real** `search_listings` tool and fake-but-realistic async
enrichment tools — including graceful degradation when a source errors
or a listing has no `state` field. (The same underlying
`get_neighborhood_demographics`/`get_safety_stats`/`get_market_trends`
functions are still exactly what gets called today — just via direct
tool calls now rather than a dedicated always-on node; see "Search
returns exactly what was asked for" above.) That's not a substitute
for trying it against your real Census/FBI keys, but it means the
wiring itself is solid before you do.
